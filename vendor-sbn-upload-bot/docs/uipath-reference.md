# UiPath Reference — Daily Vendor SBN Upload Bot

Source of truth for how this bot is built in UiPath. The reviewer checks the design's **correctness** against this doc. Rules marked ✅ are **project-adopted conventions** (our own hard constraints — non-negotiable). Rules marked ⚠️ are **believed-but-unverified platform behavior** — treat with caution, flag inline in the design with a documented fallback, and confirm before/at build.

## Platform hard constraints (✅ project-adopted)

- **R1 — Linear Sequences only.** Everything is nested `Sequence` containers. No Flowchart, no State Machine, no REFramework.
- **R2 — Single Main.xaml.** No `Invoke Workflow File`; no splitting into separate `.xaml`. All logic lives in `Main.xaml`, organized by named `Sequence` containers (`DisplayName`) as logical sections.
- **R3 — Config.xlsx at startup.** A `Config.xlsx` (Name/Value columns, sheet "Config") is read once into `configDict`. All environment-specific values (paths, URLs, credentials (per R7 — from Config or a secure store), retry/timeout numbers, email recipients) come from Config — **never hardcoded**. **Two bootstrap literals are exempt**, because they precede or point to Config and so cannot live inside it: `configPath` (where Config is), and `FallbackErrorRecipient` (who to email when the Config read itself fails — without it, a bad Config produces a silent run with no error email). Both are variable Defaults rather than step `Assign`s (P6); only `FallbackErrorRecipient` is *forced* to be a Default by the error path — `configPath` is one simply because it's a constant (and stops being a literal at all if U11's argument/asset fallback is taken — still not hardcoded either way). No third exemption.
- **R4 — Dictionary for structured data.** Use `Dictionary(Of String, String)` / `Dictionary(Of String, Object)`. Use `DataTable` only for genuine tabular row iteration (e.g. the SAP export / Excel reads).
- **R5 — Verb + Object naming.** Every activity and Sequence `DisplayName` is Verb + Object ("Read Config File", "Click Upload Button", "Assign Upload Name").
- **R6 — Windows project.** Target UiPath **Windows** project. VB.NET (and C#) expressions are acceptable; string literals are quoted (`"..."`), expressions use VB.NET syntax (`+` concatenation, `.ToString`, `CInt(...)`).
- **R7 — No credentials in the design.** Credentials are read from Config (or an Orchestrator asset / Windows Credential Manager if later chosen) — never written into the workflow or these docs.

## Standard patterns (✅ project-adopted)

- **P1 — Config read.** `Use Excel File` on `configPath` — set **`CreateIfNotExists` explicitly to False** rather than relying on its default → `Read Range` "Config" → `configTable` (DataTable) → `For Each Row` → `configDict(row("Name").ToString) = row("Value").ToString`. The flag matters: if it is True, a missing or mis-resolved `configPath` silently creates an empty workbook, so the run fails later on a confusing sheet/`Read Range` error and leaves a stray file behind, instead of failing immediately with "file not found". **U11's fail-fast claim depends on this flag** — don't change one without the other. (If the classic `Excel Application Scope` is used instead, the equivalent property is `CreateNewFile`.)
- **P2 — Retry block.** `Assign retryCount = 0` → `Do While retryCount < CInt(configDict("MaxRetry"))` → `Try Catch`: Try does the action then sets `retryCount = CInt(configDict("MaxRetry"))` to exit; Catch does `retryCount = retryCount + 1`, and if `retryCount >= MaxRetry` logs Error + `Rethrow`, else `Delay`. Any reused counter is reset before each independent retry block.
- **P3 — Logging.** `Log Message` at: bot start (Info), each phase start/end (Info), each caught error (Error, includes `exception.Message`), bot end (Info). **Warning** is reserved for *the run continued, but on a degraded path a human needs to know about* — a retry that succeeded, duplicate rows collapsed, a zero-row export treated as an empty day. A Warning that would fire on every run is not sufficient on its own: give it a delivery path into the Phase 5 summary email as well, or it becomes noise nobody reads.
- **P4 — Outer Try-Catch-Finally.** `Main` wraps Phases 1–5 in a `Try`; `Catch (Exception)` logs Error + sends the error email; `Finally` runs Phase 6 Cleanup (close apps) so it executes on every exit path.
- **P5 — SAP GUI UI automation.** Drive SAP GUI with `UiPath.UIAutomation.Activities` (SAP GUI Scripting enabled). Enter transaction codes via the command field (`Type Into`), fill selection fields, execute (`Click`/`F8`), and read results/status via SAP GUI selectors. Prefer stable SAP element IDs in selectors over screen coordinates. Wait for elements (`Element Exists` / reliable selectors) rather than fixed delays. Read the **status bar** element for messages (empty result, errors).
- **P6 — Choosing an initializer: variable Default vs. step `Assign`.** A Main-scoped **Default** is evaluated once at scope entry, before any activity runs, so it survives into the outer Catch even when an early step throws. A step **`Assign`** only takes effect if that step is reached.
  - If a variable must hold a valid value **on the error path** — anything the Catch-path error email or the Finally cleanup reads — give it a **Default**. `RunDate` and `FallbackErrorRecipient` are the cases in point: a step assign placed after config validation leaves `DateTime.MinValue` in the error email, and a step assign for the fallback recipient is safe only for as long as nobody inserts an activity ahead of it.
  - If it's only read on paths that run after its assign, a step `Assign` is fine and reads more explicitly — `EmptyResultFlag` and `VendorIDs` (assigned in Phase 1's control-variable init step).
  - Note this does **not** license a Default that references another variable: `vendorData = sapData.Clone` as a Default would evaluate at scope entry while `sapData` is still `Nothing`. Defaults must be self-contained literals or expressions over constants.
  - Write Defaults in language-agnostic form (`DateTime.Today`, not VB's `Today`) per R6.

## Packages (expected)

- `UiPath.Excel.Activities` — Config read, SAP export read, SBN template read (CSV or Excel), CSV write.
- `UiPath.System.Activities` — core (Assign, If, Try Catch, Delay, logging).
- `UiPath.UIAutomation.Activities` — SBN web portal automation.
- `UiPath.Mail.Activities` (or Outlook via `UiPath.MicrosoftOffice365` / SMTP) — summary/error email. (Exact mail mechanism TBC.)
- SAP GUI automation: handled via **`UiPath.UIAutomation.Activities`** driving the SAP GUI directly (SAP GUI Scripting must be enabled — UiPath's SAP selectors are built on it). No `.vbs`, no separate SAP package needed for GUI screen automation.

## Unverified platform behaviors (⚠️ — confirm before build)

- **U1 — RETIRED.** (Was: Invoke Code/VBScript for a SAP `.vbs`.) Superseded by native UiPath SAP UI automation — no `.vbs` is used. Kept as a placeholder so later U-numbers don't shift.
- **U2 — SAP "no values found" detection.** The empty-day check reads SAP's **status-bar text directly in UiPath** (`Get Text` on the status-bar element) after executing the SQVI query, and tests it for the no-records message. Exact message text and the status-bar selector to be confirmed live. Fallback: treat a zero-row export as the empty case.
- **U3 — SBN upload-row identification & status read.** Locating the just-created row by its unique Name and reading its Status cell via UI selectors — selector reliability to be confirmed against the live portal. Fallback: sort by Last Updated / anchor on the Name text.
- **U4 — `Use Excel File` / `Excel Application Scope` auto-closes on exception.** The design assumes the Excel scope releases the workbook on both success and error (so Finally has nothing to close for the config read). Believed correct but unverified. Fallback: an explicit `Close Workbook` / kill stray Excel in Phase 6 cleanup.
- **U5 — SAP create-date filter format.** The value UiPath types into the SQVI query's create-date (ERDAT) selection field is locale-dependent (SAP display format, e.g. `dd.MM.yyyy` vs `MM/dd/yyyy`) and must match the SAP user's date format. Unverified until tested live. Fallback: confirm the format from a manual query run and set it explicitly; keep it a Config value if it varies by environment.
- **U6 — RETIRED.** (Was: `.vbs`→UiPath result-token file contract.) No longer needed — UiPath reads the SAP status bar directly (U2) and drives the export itself (U7), so there is no cross-boundary result file. Kept as a placeholder so later U-numbers don't shift.
- **U7 — SAP ALV export to local file via UiPath.** Exporting the SQVI result grid to `ExportPath` by driving the SAP menu (System → List → Export → Local File → Spreadsheet, or the toolbar export button) with UI activities — exact menu path, the file-format dialog, and overwrite/replace handling to be confirmed live. Fallback: alternate export format (e.g. text/`.xls`) or read the ALV grid directly — **note this fallback is not free-standing**: changing the export format also forces U10's reader fallback, since Phase 3 reads the file with `Use Excel File` + `Read Range`. And the "read the ALV grid directly" half goes further — it removes the export file altogether, so Phase 2 step 4.Try.6.a (clear stale file) and 6.c (missing-file Throw + row-count validation) lose their subject and would need replacing with a grid row-count check. Choose these together, not in isolation.
- **U8 — SBN template & output-file format (both directions).** *(Distinct from **U10**, which covers the SAP export artifact; U8 is entirely about the SBN-side files.)* *Writing:* the output CSV must match what SBN's uploader accepts — field delimiter (assumed comma), text encoding (e.g. UTF-8), quoting/escaping of values containing commas, and whether a header row is required. *Reading:* Phase 3 step 4 also builds its output columns by reading the **SBN template**, so the same delimiter/encoding assumptions apply there, plus the template's actual format (`.csv` vs `.xlsx`, still open under Open Item #3) and the need for headers to be read as headers — `Read CSV` with "Include column names" = False silently yields `Column1..N` and would hardcode nothing but junk column names. To be confirmed against a known-good SBN template/sample. Fallback: match the byte format of a manually-exported working file exactly (delimiter, encoding, line endings).
- **U9 — SQVI query navigation & selection.** Driving SQVI to select the named query (`SAPQueryName`) and reach its selection screen — exact steps (SQVI opens on a query list vs. last query; how to pick the query; Execute) and behavior when the query is absent for the login user, to be confirmed live. Note SQVI queries are **user-specific** — the query must exist under (or be shared to) the bot's SAP user (see PDD Prerequisites). Fallback: run the query's generated program directly, or use a global InfoSet query the bot user can access.
- **U10 — SAP export file shape.** What the exported file actually looks like once written: the real format produced (`.xlsx` vs `.xls` vs tab-delimited text), which row the column headers land on, and whether SAP prepends preamble/title rows. Two steps depend on this shape: medium-level design **Phase 3 step 2** reads the file with a plain `Read Range` on `ExportPath`, and **Phase 2 step 4.Try.6.c** counts its rows to validate the export — both assuming a clean sheet with headers in row 1. The Phase 2 dependency is the sharper one, and it can fail in both directions: an export with **no header row** loses its only data row to the header, so a 1-vendor day counts zero and routes silently to the "nothing to process" email rather than failing; **preamble rows** inflate the count instead, passing a garbage row to Phase 3. Distinct from **U7**, which covers *driving* the export (menu path, dialog, overwrite handling); U10 covers the resulting *artifact*. To be confirmed from a sample export. Fallback: `Read Range` with an explicit range/offset to skip preamble rows, or read the ALV grid directly instead of exporting.
- **U11 — Relative path resolution.** `configPath`'s Default is the bare relative literal `"Config.xlsx"`, which assumes UiPath resolves relative paths against the project/package folder at runtime — true when run from Studio, unconfirmed for an Orchestrator-deployed package where the working directory may differ. Fallbacks, in order of preference: (a) supply an **absolute path** from outside the workflow — a Main `in_ConfigPath` argument fed by an Orchestrator process setting, or an Orchestrator asset — which anchors on something that is not the working directory; (b) **pin the working folder** in the Orchestrator process settings. Note what does *not* work: `Path.Combine(Directory.GetCurrentDirectory(), "Config.xlsx")` resolves against the working directory, which is precisely what a bare relative literal already does — it is the same behavior spelled longer, not a remedy. If the argument route is taken, treat a blank/unset `in_ConfigPath` as "use the `"Config.xlsx"` Default" rather than passing `Nothing` through — otherwise a forgotten Orchestrator setting throws a null-argument error instead of the clear "file not found" this rule is trying to preserve. Confirm at the first unattended run. Unlike U2/U10, getting this wrong fails Phase 1 step 4 immediately and loudly — a fail-fast assumption, not a silent one, **but only because P1 pins `CreateIfNotExists = False`**; if that flag ever changes, this stops being fail-fast.

## Lessons Learned

- **L1 — The SQVI query returns duplicate rows: 2 rows per vendor with identical values.** *(Live result reported by user, 2026-08-14. This is a **data-source** lesson about the SAP query, not a UiPath-platform rule.)*
  - **Assumed:** the query yields **one row per vendor**, guaranteed by the `ADR6.FLGDEFAULT = 'X'` default-email filter. Phase 3's de-dup step was designed as a *safety net* against a stray duplicate (medium-level design Phase 3 step 3).
  - **Actually true:** vendors come back **twice**, with identical values in the output columns. *(Reported as "each vendor has 2 rows"; whether that holds for **every** vendor or only the ones inspected has not been checked — the distinction matters, see the hypotheses.)*
  - **Consequence for the design:** the de-dup step is no longer a safety net, it is **load-bearing**. Without it the CSV would upload every vendor twice. It stays in the design regardless of how the query is fixed.
  - **Root cause: under diagnosis.** Note the shape of the evidence constrains the candidates — a fan-out that affects **only some** vendors is data-dependent (address versions, extra email records), while one affecting **every** vendor points at the join or the extraction itself:
    1. **ADRC fan-out on address versions** *(data-dependent).* ADRC is keyed by `ADDRNUMBER` + `NATION` + `DATE_FROM`; a vendor with a translated/international address version yields 2 ADRC rows, and since no mapped column is read from ADRC, both rows print identically.
    2. **ADR6 joined on `ADDRNUMBER` alone, without restricting `PERSNUMBER = ''`** *(data-dependent).* Contact-person emails sit in ADR6 under a non-blank `PERSNUMBER` alongside the address-level email; `DATE_FROM` can add a second dimension. Note a **`CONSNUMBER` duplicate cannot explain identical rows** — `CONSNUMBER` sequences *distinct* communication records, so it would produce two rows with *different* emails.
    3. **Something other than the address join** *(fits a uniform 2×).* An extra table in the query (e.g. LFB1 company-code or LFM1 purchasing-org data, which have their own keys and multiply per vendor), or an export/list artifact rather than a join fan-out at all.
  - **Diagnosis:** for one affected vendor's `LFA1~ADRNR`, count rows in **ADRC** and in **ADR6** for that `ADDRNUMBER`. Whichever returns 2 is the culprit. **If both return 1**, the fan-out is not in the address join — inspect the query's full table list and join conditions, and re-export to rule out a list/export artifact. Then check whether the duplication affects *all* vendors or only some.
  - **Design implication if ADRC is the cause — conditional:** ADRC may contribute **no output column at all**, in which case dropping it removes the fan-out at source rather than masking it, leaving the join as **LFA1 ⋈ ADR6**. **This holds only if City and Country really come from LFA1 (`ORT01`/`LAND1`) rather than ADRC (`CITY1`/`COUNTRY`)** — the mapping table's source columns are still `(TBC)` placeholders under Open Item #4, and PDD Prerequisites contemplates "postal fields in ADRC/LFA1". Confirm against the sample export before dropping ADRC, or two mapped columns break. If ADRC is dropped, every doc describing the join as `LFA1 ⋈ ADRC ⋈ ADR6` must be swept in the same pass.
  - **Do not "fix" this by de-duplicating alone.** A join returning 2 rows per vendor today can return 3 tomorrow, and a fan-out that silently collapses is indistinguishable from one that quietly drops the row you wanted (e.g. picking the blank-email row of a pair).
  - **Acceptance criterion for closing this:** a re-run whose export has **row count == distinct Vendor ID count**, with vendors that have no default-flagged email still present carrying a **blank** email.
